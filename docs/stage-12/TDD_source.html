1. Executive summary

CampusOS lets a campus keep running when the internet does not. Faculty take attendance on a phone, even offline; the data waits safely on the device and syncs without duplicates. The Office Admin manages academic masters, internal marks (with moderation and locking), simulated fee ledgers, and an evidence-based view of students who may need attention. A deterministic rules engine decides risk; an optional AI layer may only explain the rule evidence and fails closed.

2. Business problem

Campus operations (attendance, marks, fees) depend on connectivity that classrooms often lack. Paper registers get re-keyed, marks change without a trail, and early warning for struggling students arrives too late. The product must therefore (a) never lose attendance, (b) make every sensitive change auditable, and (c) separate decisions (rules) from explanations (AI).

3. Proposed solution and MVP scope

A web application (Next.js) talking to a single authoritative API (FastAPI) backed by PostgreSQL on Supabase. Attendance is written to IndexedDB first, queued, and replayed idempotently.

5. Requirements (summary)

  • Functional: authenticated access; role-scoped data; offline attendance with idempotent sync and conflict reporting; marks validation and lifecycle (draft, submitted, moderated, locked); fee ledger with partial payments; deterministic risk categories with stored evidence; mentor tasks with human approval; audit of important actions.
  • Non-functional: no data loss on failure; responsive 360-1440 px; 44 px touch targets; no secrets in Git; documented limits.
  • Sample record that must match: Subhashree Mohanty · ENG-24-CSE-0412 · B.Tech CSE · Year 2 · attendance 81.5% · internals 33/40 · fee due ₹0 (seeded and asserted in tests).

9. API architecture

REST under /api/v1 with a uniform error envelope {"error": {"code","message","details"}}. Public: /health, /ready. Everything else requires a Bearer token. Main groups: me; masters (programmes, academic-years, batches, subjects, faculty, assignments); students; attendance (roster, sessions, sync, correction); assessments + moderation; accounts, payments, receipts; insights, mentor-tasks; audit; overview.

10. Authentication and authorisation

  1. The browser signs in with Supabase and receives a JWT.
  2. Every API call carries it; FastAPI verifies signature (JWKS), audience and expiry, then loads the user’s profile (role, campus, faculty id).
  3. Dependencies require_admin / require_faculty guard routes; faculty queries are additionally scoped by teaching assignments; out-of-scope ids answer 404 (no existence signal).

The frontend guard only improves UX; the API is the enforcement point.

11. Attendance architecture and offline synchronisation

  1. Write IndexedDB first: Save stores the complete session (the exact /attendance/sync body) in a Dexie outbox in one transaction, tagged with the profile id.
  2. Client UUID idempotency key = outbox id. Replays send the same key; the server returns the existing session (200) instead of creating a duplicate.
  3. Sync runner (single-flight) triggers on load, online, tab visible, a 30 s tick and manual retry; exponential backoff 2 s to 5 min.
  4. Server checks: JWT, assignment, students in batch, complete roster, status values; unique constraints as the final guard.
AnswerOutcome (local data always kept)
200/201synced
network errorstays pending, queue pauses
401stays pending; "Sign in again to sync"
5xx/408/429failed, retried with backoff or manually
403/404/422failed, not retryable
409conflict shown for review; never silently merged

The header chip reads navigator.onLine and the live outbox counts: conflict, failed, syncing, waiting, offline, synced. Rosters and class lists are cached per profile for offline marking; a roster that was never cached produces an honest message, not an empty list. No tokens or fee data are stored locally. Logout keeps pending records; another profile cannot send them.

Limit: there is no Service Worker, so pending records sync the next time the app is opened online. The full browser journey (reload and close/reopen while offline, then reconnect) was tested with fake-indexeddb, not yet in a real signed-in browser.

12. Internal marks and moderation

Lifecycle: draft → submitted (faculty, all students scored) → moderated (admin) → locked (admin). Scores are validated (number, not negative, not above max, 2 decimals). Faculty edit only drafts; admins may edit submitted/moderated marks with a mandatory reason; locked marks are read-only until an admin unlocks them with a reason. Every score and state change writes a history row shown in the UI.

13. Fee management

Exact decimal arithmetic. Partial payments allowed, overpayment rejected (client and server). Each payment has an idempotency key; a replay returns the same receipt. Every amount is labelled simulated; no payment gateway exists. Reconciliation totals shown on the Fees list are per page.

14. AI student intelligence

InputRule (version rules-v1)Label
Attendance< 65% severe; 65% to < 75% shortage (75% is the stated line)High / Moderate
Internals< 40% of maxHigh
No datanothing recordedInsufficient data

The 65% and 40% thresholds are our documented choices, not institutional policy. The AI layer receives rule output only (no names or ids), must return validated JSON, may not contain numbers absent from the evidence, and on any failure the screen shows the deterministic evidence plus an "AI explanation unavailable" note. It never writes marks, attendance, fees or tasks. Mentor tasks require an explicit "Approve and create task". No AI key is configured, so no live model output exists.

Constraints. DPDP 2023: the demo uses synthetic data only (plus the one specified sample record); parental consent for minors, data-principal rights and retention are not modelled and would be required before real use. Campus/department scoping is enforced for faculty through teaching assignments; per-campus roles for several campuses are not built. Marks lock after moderation with a full change log. Results-day load (7,800 students at once) was not load tested. Weak classroom Wi-Fi is the reason for the offline-first design.

19. Limitations

  • No signed-in browser verification, no PostgreSQL run, no live AI call, no Lighthouse/axe/screen-reader pass.
  • No Service Worker background sync; no rate limiting; no CSP.
  • Academic model has no separate semester/department entities (one programme; a class = year + section).
  • Mentor task form lacks assignee and completion-note fields; no student create/edit UI; no dashboard trend cards; fee reconciliation is per page.

20. Future improvements

Service-Worker background sync; push of conflict resolution to the admin; rate limiting and CSP; Postgres-backed CI with Playwright journeys for both roles; semester/department entities; mentor assignment and notes; campus-wide fee reconciliation; multi-campus support.
